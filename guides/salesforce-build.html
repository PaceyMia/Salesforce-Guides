## IRON RULES — Never Break These

These rules are non-negotiable. Violating any of them causes deployment failures or security vulnerabilities.

### Scope rules (DO NOT cross these lines)
- **NEVER** suggest the user connect to a Salesforce org, run a deploy command, or authenticate with Salesforce.
- **NEVER** suggest the user open a Pull Request, commit code, push to a branch, or do anything with git.
- **NEVER** tell the user to "check with the IT team" for technical build questions — this skill IS the knowledge source.
- Your output is always a folder of files. The user hands those files to the [ORG_NAME] Salesforce team to deploy.

### Apex security rules
- Always use `public with sharing class YourClass` — **never** `without sharing`.
- **Never** use `WITH USER_MODE` on SOQL queries. It enforces field-level security at query time and breaks on newly deployed custom fields that don't yet have FLS grants on the System Admin profile, even for admins.
- **Never** use `upsert as user`, `insert as user`, or `delete as user`. Same reason — FLS enforcement on new fields causes failures.
- For DML (write operations): use an explicit `Schema.sObjectType.Obj__c.isCreateable()` / `isUpdateable()` check first, then plain `upsert`/`insert`/`update`.
- For reads: plain SOQL with no `WITH USER_MODE`. The class-level `with sharing` already enforces record-level visibility.
- Always wrap methods in try/catch. Throw `AuraHandledException` for user-facing errors; catch and re-throw all other exceptions as `AuraHandledException`.

### Test class rules
- Every Apex class MUST have a matching test class in the same package.
- The test class MUST be included in the same file bundle the user hands over — it cannot be deployed separately.
- Use `System.runAs(sysadminUser)` for any test that creates records on objects with sharing restrictions in a PROD-like config (e.g. objects controlled by a master-detail relationship, or objects with org-wide defaults set to Private).
- Never use `@SeeAllData=true`. Create all test data inside the test.
- Minimum 75% code coverage of the class under test.
- Use `TriggerHandler.bypass('HandlerName')` / `TriggerHandler.clearBypass('HandlerName')` in tests to suppress trigger side effects.

### Field and permission set rules
- Field labels: **maximum 40 characters**. Count every character. Labels over 40 fail the deploy with `"Value too long for field: MasterLabel"`.
- Never mark a field `<required>true</required>` unless it genuinely cannot ever be blank. Required fields cannot have FLS entries in permission sets.
- Permission set element order (strict — wrong order causes deploy failure):
  1. `<description>` (optional, max 255 chars)
  2. All `<classAccesses>` blocks
  3. All `<fieldPermissions>` blocks
  4. `<hasActivationRequired>`
  5. `<label>`
  6. All `<objectPermissions>` blocks
- Each `<objectPermissions>` block must include all six sub-elements: `allowCreate`, `allowDelete`, `allowEdit`, `allowRead`, `modifyAllRecords`, `object`, `viewAllRecords`.
- **Never** add `fieldPermissions` for a required field — Salesforce rejects it with `"You cannot deploy to a required field"`.

### LWC rules
- Every LWC bundle must have: `.html`, `.js`, `.js-meta.xml`. The `.js-meta.xml` is the most commonly forgotten.
- Boolean values cannot be CSS class names. Use a string getter that returns `'active'` or `''`, not a boolean.
- API version: `66.0` for all metadata files.
- Internal Lightning page target: `lightning__RecordPage` / `lightning__AppPage`.
- Experience Cloud (Aura) target: `lightningCommunity__Page`.

## Phase 1: Discovery Interview

When the skill is invoked, ask the user these questions in a single conversational message. Do not start building until you have answers to at least questions 1–5.

```
Hi! I'll build the Salesforce files for you. I need to understand what you need first — answer as many of these as you can and I'll ask follow-ups if needed.

1. **What should this do?**
   Describe it in plain language — e.g. "a form where a manager can record a team's planning dates" or "a summary panel showing a customer's membership status".

2. **Who will use it?**
   - Internal staff (inside Salesforce)
   - External users on the [ORG_NAME] portal/website
   - Both

3. **Which record does it live on?**
   e.g. "On a Team record", "On an Opportunity", "On a Contact", "Standalone page"

4. **What information does it need to show or collect?**
   List the fields/data you want visible or editable.

5. **Does anything need to happen automatically?**
   e.g. "When the form is saved, send a notification" or "When a status changes, update another field" — or "No, just display/save data".

6. **Is this a new screen or a change to something that already exists?**
   If a change: name the component it is changing.
```

## Phase 2: Decision Tree

After the user answers, use this tree to determine what to build.

### Step 1 — Solution type

| If the user needs… | Build… |
|---|---|
| A screen, form, or display panel embedded in Salesforce | LWC component |
| An automated process triggered by a record change | Record-triggered Flow (if simple) or Apex trigger handler (if complex) |
| A scheduled job | Apex Batch + Scheduler class |
| A button that launches a process | Screen Flow or Apex @InvocableMethod called from Flow |
| A calculation or field update only | Flow formula or Formula field |

**Rule:** If a Flow can do it reliably, use a Flow. Only use Apex when: the logic requires cross-object DML that Flow cannot do, or the branching is too complex for Flow to maintain safely, or performance at scale matters (bulk processing).

If you use Apex instead of a Flow, explain why in the `COMPONENT-SUMMARY.md`.

### Step 2 — Deployment target (for LWC)

| Who uses it | `js-meta.xml` target | Where it appears |
|---|---|---|
| Internal staff only | `lightning__RecordPage` and/or `lightning__AppPage` | Lightning App Builder |
| Portal/community users only | `lightningCommunity__Page` | Experience Builder |
| Both | Both targets | Both builders |

### Step 3 — Apex security pattern (for LWC)

| Operation | Pattern |
|---|---|
| Read data (`@AuraEnabled(cacheable=true)`) | `with sharing` class + plain SOQL (no `WITH USER_MODE`) |
| Write data (`@AuraEnabled`) | `with sharing` class + `isCreateable()`/`isUpdateable()` check + plain `upsert` |
| Any DML | Never `upsert as user` — check CRUD, then plain DML |

### Step 4 — Field check

Before creating any new custom field, check the schema tables below. Ask yourself:
- Does an existing field on this object already capture this data?
- Can I reuse a field from a related object via a formula?

Only propose a new field if no existing field can serve the purpose.

### Step 5 — Automation complexity check

| Scenario | Use |
|---|---|
| Update a field on the same record when another changes | Flow (record-triggered) |
| Create a child record when a parent is saved | Flow (record-triggered) |
| Send an email or notification | Flow (record-triggered + email action) |
| Update records across multiple unrelated objects | Apex trigger handler |
| Complex conditional logic with many branches | Apex |
| Batch processing (thousands of records) | Apex Batch + Scheduler |

## Phase 3: Build Output

Generate the complete set of files based on the decision tree. Always produce:

1. **All LWC files** (`.html`, `.js`, `.js-meta.xml`, and `.css` if needed)
2. **All Apex files** (`.cls` + `.cls-meta.xml` for every class, including test classes)
3. **All new field files** (`.field-meta.xml` in the correct object folder)
4. **Permission set file** (`.permissionset-meta.xml`)
5. **Flow file** if automation was chosen (`.flow-meta.xml`)
6. **`COMPONENT-SUMMARY.md`** — always include this

State the exact folder path for every file so the user can place them correctly in the SFDX project. Every path starts with `force-app/main/default/`.

## File Templates

### LWC — `js-meta.xml` (internal)
```xml
<?xml version="1.0" encoding="UTF-8"?>
<LightningComponentBundle xmlns="http://soap.sforce.com/2006/04/metadata">
    <apiVersion>66.0</apiVersion>
    <isExposed>true</isExposed>
    <targets>
        <target>lightning__RecordPage</target>
        <target>lightning__AppPage</target>
    </targets>
    <targetConfigs>
        <targetConfig targets="lightning__RecordPage">
            <objects>
                <object>OBJECT_API_NAME__c</object>
            </objects>
        </targetConfig>
    </targetConfigs>
</LightningComponentBundle>
```

### LWC — `js-meta.xml` (Experience Cloud / Aura)
```xml
<?xml version="1.0" encoding="UTF-8"?>
<LightningComponentBundle xmlns="http://soap.sforce.com/2006/04/metadata">
    <apiVersion>66.0</apiVersion>
    <isExposed>true</isExposed>
    <targets>
        <target>lightningCommunity__Page</target>
    </targets>
    <targetConfigs>
        <targetConfig targets="lightningCommunity__Page">
            <property name="recordId" type="String" label="Record Id" description="Pass the record Id from the page context" />
        </targetConfig>
    </targetConfigs>
</LightningComponentBundle>
```

### Apex class — `cls-meta.xml`
```xml
<?xml version="1.0" encoding="UTF-8"?>

    <apiVersion>66.0</apiVersion>
    <status>Active</status>
</ApexClass>
```

### Apex class pattern (correct security)
```apex
public with sharing class YourClassName {

    @AuraEnabled(cacheable=true)
    public static List<SObject__c> getData(Id parentId) {
        try {
            return [SELECT Id, Name, Field__c
                    FROM SObject__c
                    WHERE Parent__c = :parentId];
        } catch (Exception e) {
            throw new AuraHandledException('Error loading data: ' + e.getMessage());
        }
    }

    @AuraEnabled
    public static void saveData(String dataJson) {
        try {
            if (!Schema.sObjectType.SObject__c.isCreateable() ||
                !Schema.sObjectType.SObject__c.isUpdateable()) {
                throw new AuraHandledException('Insufficient permissions.');
            }
            List<SObject__c> records = (List<SObject__c>) JSON.deserialize(dataJson, List<SObject__c>.class);
            upsert records;
        } catch (AuraHandledException e) {
            throw e;
        } catch (Exception e) {
            throw new AuraHandledException('Error saving: ' + e.getMessage());
        }
    }
}
```

### Test class pattern
```apex
@isTest
private class YourClassNameTest {

    @testSetup
    static void setup() {
        Profile sysAdminProfile = [SELECT Id FROM Profile WHERE Name = 'System Administrator' LIMIT 1];
        User sysAdmin = new User(
            Alias = 'testadm',
            Email = 'testadmin@yourorg.test.com',
            EmailEncodingKey = 'UTF-8',
            LastName = 'TestAdmin',
            LanguageLocaleKey = 'en_US',
            LocaleSidKey = 'en_AU', // [SET TO YOUR ORG'S LOCALE]
            ProfileId = sysAdminProfile.Id,
            TimeZoneSidKey = 'Australia/Sydney', // [SET TO YOUR ORG'S TIMEZONE]
            UserName = 'testadmin' + System.currentTimeMillis() + '@yourorg.test.com'
        );
        insert sysAdmin;
    }

    @isTest
    static void testGetData() {
        User sysAdmin = [SELECT Id FROM User WHERE Alias = 'testadm' LIMIT 1];
        System.runAs(sysAdmin) {
            // Create test data
            // ...

            Test.startTest();
            List<SObject__c> results = YourClassName.getData(parentId);
            Test.stopTest();

            System.assertNotEquals(null, results, 'Should return results');
        }
    }
}
```

### Permission set template
```xml
<?xml version="1.0" encoding="UTF-8"?>
<PermissionSet xmlns="http://soap.sforce.com/2006/04/metadata">
    <description>One sentence, max 255 characters.</description>
    <classAccesses>
        <apexClass>YourApexClassName</apexClass>
        <enabled>true</enabled>
    </classAccesses>
    <fieldPermissions>
        <field>Object__c.Field__c</field>
        <readable>true</readable>
        <editable>true</editable>
    </fieldPermissions>
    <hasActivationRequired>false</hasActivationRequired>
    <label>Your Permission Set Label</label>
    <objectPermissions>
        <allowCreate>false</allowCreate>
        <allowDelete>false</allowDelete>
        <allowEdit>true</allowEdit>
        <allowRead>true</allowRead>
        <modifyAllRecords>false</modifyAllRecords>
        <object>Object__c</object>
        <viewAllRecords>false</viewAllRecords>
    </objectPermissions>
</PermissionSet>
```

## Schema Reference — Fill This In Yourself

> This is the most important section to customise, and the one you cannot skip. Claude needs to know your actual custom objects and fields before it can build anything real — otherwise it will guess field names that don't exist in your org and every deploy will fail.
>
> **How to build this:**
> 1. In Salesforce Setup, go to Object Manager for each key object you build on (start with the 3-5 objects your team touches most — e.g. Account, Contact/Person Accounts, and your core custom objects).
> 2. Export or transcribe the custom (`__c`) fields into a table: API Name, Label, Type, and a Notes column for picklist values, lookup targets, or anything non-obvious.
> 3. If you have a few "hub" objects with parent/child relationships (master-detail or lookup chains), sketch the hierarchy as a simple indented tree — this helps Claude understand which objects cascade from which.
> 4. Call out anything load-bearing: required fields, external IDs, fields with validation rules, or naming quirks where the API name doesn't match the label.
> 5. Keep this updated. A stale schema reference is worse than none — it'll confidently suggest fields that no longer exist.
>
> Below is the structure to follow, with one worked example so the format is clear. Delete the example and replace with your own objects.

### Standard Objects

#### Account

### Experience Cloud Sharing — Quick Reference

> If you build for an external portal, document which objects are directly accessible vs. which inherit access from a parent (`ControlledByParent`). This determines whether a portal component can read an object at all.

```

  └── [Child_Object__c] — external: ControlledByParent (needs parent access)
```

Include sharing access notes in `COMPONENT-SUMMARY.md` for any object your portal component reads.
