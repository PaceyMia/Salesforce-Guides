Component conventions that hold for any brand:
- Component shell: use a custom div wrapper, NOT <lightning-card>. Full visual control, clearly
  separates your component from surrounding Salesforce chrome.
- Tables: custom HTML <table>, NOT <lightning-datatable>. You control rows, hover, borders, badges.
- Status badges: inline <span> pills. Keep one colour per status, consistent across components.
- Components should look modern — rounded corners, soft shadows, smooth hover. People compare
  against SaaS UI, not classic Salesforce.

## Apex standards
### Sharing model
Choose deliberately and document why.
- Use `with sharing` by default — it respects record-level security.
- Use `without sharing` ONLY when a display component must show contextual data that the running
  user's profile can't reach through sharing, AND the data is safe for anyone who can open the
  record to see. Document the reason in a comment. Never reach for it just to make an error go away.

### Error handling
Wrap the method body in try/catch and throw AuraHandledException:
```apex
@AuraEnabled(cacheable=true)
public static List<MyRow> getData(Id recordId) {
    try {
        // query logic
        return rows;
    } catch (Exception e) {
        throw new AuraHandledException('Error loading data: ' + e.getMessage());
    }
}
```

### Inner classes
Return typed inner classes from @AuraEnabled methods — never raw SObject lists:
```apex
public class MyRow {
    @AuraEnabled public String fieldOne;
    @AuraEnabled public Date fieldTwo;
}
```

## Permission sets — mandatory for every LWC
Every LWC with an Apex controller needs a dedicated permission set granting class access — most
profiles don't grant it by default. Create [Feature]_LWC.permissionset-meta.xml granting the
controller's Apex class, and deploy it alongside the component. Assign it before testing as a
non-admin user.

## LWC patterns
### Wire adapters
- @wire(getRecord, { recordId: '$recordId', fields: FIELDS }) for record fields shown in the
  component — auto-refreshes when the record is saved on the page.
- @wire(MyApexMethod, { param: '$recordId' }) for Apex data.
- Import displayed record fields into the LWC so it reacts to inline edits.

### State handling — handle all four, always
1. Loading (until the wire resolves)
2. Error (wire returns an error)
3. Data with results
4. Empty (wire returns an empty array)
Empty states should be compact and specific — plain wording about why nothing is shown.

## Schema reference — replace with your own
Document the objects this skill will touch so Claude stops guessing field names. Example format:
```
[OBJECT]__c
    [Lookup_Field]__c  -> [Parent Object]
    [Date_Field]__c    -> Date
    [Status_Field]__c  -> Picklist
```
Note any quirks: fields where the API name differs from the label, values stored as text to avoid
conversion, status-priority rules. A stale schema reference is worse than none.

## Test class standards
- Minimum coverage 75% for production; aim higher.
- Cover: happy path, alternative logic paths, boundary conditions, empty results return [] not null,
  null/missing optional fields, data isolation, edge cases.
- Use System.runAs() with a standard-user profile to confirm no exceptions for non-admins.
- Use Assert.areEqual()/Assert.isNotNull(), not the deprecated System.assertEquals.

## Checklist before every deploy
- [ ] Sharing model chosen deliberately and documented
- [ ] Try/catch wrapping the method body
- [ ] Permission set created and included in the deploy
- [ ] Test class present, all passing, meaningful coverage
- [ ] All four states handled; empty state compact and specific
- [ ] Brand tokens used, not default SLDS blue
- [ ] No <lightning-card> or <lightning-datatable> — custom markup
A font note that trips everyone up A custom web font won't load inside an LWC just by naming it in CSS — it needs to be set up as a static resource in the org, or it silently falls back. Confirm yours is wired up before you rely on it, or keep a system-font fallback in the stack.
