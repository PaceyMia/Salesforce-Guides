Claude Code, Step by Step

A plain-English guide to connecting Claude Code (the CLI/IDE agent) directly to your Salesforce org over MCP — no browser, no clicking around Setup to find records. Ask in natural language, Claude reads and writes real data through Salesforce's own hosted MCP server.
Based on Salesforce's Try Headless 360 workshop — I ran this session for Sydney last week.

Updated Jul 25, 2026
⚠ Before you start Do this in a Developer Edition org or a Sandbox — never your production org. The permission set and connected app you'll create can create, update, and delete records once authorised. Get comfortable here first.

No org yet? Sign up free at developer.salesforce.com/free-trials. You'll also need a Claude account — Claude Code installed if you're following Phases 1–5, or just the chat app at claude.ai if you're going straight for the optional Phase 6 instead.

1
Turn on the MCP Service in Salesforce
One checkbox in Setup unlocks MCP for the whole org. ~2 min
What is MCP? Model Context Protocol is the open standard AI tools like Claude use to talk to live systems instead of guessing. Without it, Claude works from memory and generic training data. With it, Claude calls real tools against your real org — query records, create a case, update a field — and gets the truth back, in the moment it needs it.
1
Enable the MCP Service (Beta)

In Salesforce, click the gear icon → Setup. In Quick Find, search User Interface and open it.

Tick Enable MCP Service (Beta) under the Setup section, then click Save.

✓ That's the org-wide switch Everything else in this guide — the permission set, the server activation, the connected app — only becomes available once this checkbox is on.
2
Create a Permission Set for the MCP Client
Controls exactly what Claude is allowed to see and do in your org. ~5 min
1
Create the permission set

In Setup Quick Find, search Permission Sets and open it. Click New.

Label: MCP Client User (the API Name fills in automatically as MCP_Client_User). Description: "Grant API access to the Salesforce hosted MCP servers." Click Save.

2
Turn on API Enabled

On the permission set you just created, click System Permissions. Click Edit, tick API Enabled, then Save.

Why this matters API Enabled is what lets a user authenticated through this permission set access any Salesforce API — including the MCP endpoint Claude Code will be calling.
3
Assign the permission set to yourself

On the permission set, click Manage Assignments → Add Assignment. Check your own user (and any other approved admins who'll use Claude Code against this org), click Next → Assign → Done.

3
Activate a Standard MCP Server and Grab Its URL
Salesforce ships several pre-built MCP servers — pick the one that matches how much access you want to hand over. ~3 min
Standard serverWhat it exposesTools
sobject-allFull CRUD — create, read, update, delete, query and search — across all objects11 + 2 prompts
sobject-readsRead and query only, no mutations6
sobject-mutationsCreate and update only, no delete9
sobject-deletesDelete operations only8
salesforce-api-contextLets Claude inspect your org's objects, fields and relationships without touching data6
⚠ Start narrow First time round, activate sobject-reads or salesforce-api-context — let Claude look before it can touch anything. Move to sobject-all once you trust the workflow.
1
Find the server in the API Catalog

In Setup Quick Find, search MCP Servers and open it (it sits under API Catalog). Click Salesforce Servers, then open the server you want (e.g. sobject-all).

2
Activate it and copy the Server URL

Click Activate. Once active, copy the Server URL shown on the Details tab — it looks like:

Server URL — copy this https://your-instance.my.salesforce.com/platform/mcp/v1/alpha/servers/sobject-all

You'll paste this into Claude Code in Phase 5. Keep this tab open, or paste it into a notes file for now.

4
Create an External Client App (the OAuth front door)
This is what Claude Code authenticates against — it's how Salesforce knows to trust the connection. ~10 min
Why an External Client App? Claude Code is a "headless" agent — it never opens the Salesforce UI. Instead it authenticates with OAuth 2.0 against an External Client App (ECA), which then restricts what it can do based on the permission set, profile and IP ranges you assign to it. Same security model as any other connected app, just built for agents instead of browsers.
1
Enable PKCE at the org level

Setup Quick Find → OAuth and OpenID Connect Settings. Enable PKCE (Proof Key for Code Exchange) if it isn't already on. This lets Claude Code authenticate securely as a public client, without needing to hard-code a secret.

2
Create the External Client App

Setup Quick Find → External Client App Manager → New External Client App.

Name it something recognisable, e.g. Claude Code MCP App. Fill in a contact email and distribution state (Local is fine for a dev org).

3
Enable OAuth and set the callback URL

Tick Enable OAuth. For the Callback URL, use a fixed localhost port — Claude Code listens on your machine for the OAuth redirect, it isn't a hosted web app like claude.ai:

Callback URL http://localhost:8080/callback
⚠ Remember this port number Whatever port you enter here (8080 is just a suggestion — pick any free port) has to match the --callback-port you'll pass to claude mcp add in Phase 5. A mismatch is the single most common reason this OAuth flow fails.
4
Add the OAuth scopes

Add these two scopes:

♻
Perform requests at any time (refresh_token, offline_access) — so Claude Code doesn't need you to re-authenticate every session
MCP
Access Salesforce hosted MCP servers (mcp_api) — the scope that actually grants MCP access

Click Create.

5
Lock down the security settings

Open the app you just created → Edit App Policy. Under Security:

✗ Require secret for Web Server Flow — leave unchecked
✗ Require secret for Refresh Token Flow — leave unchecked
✓ Require PKCE — check this
✓ Issue JSON Web Token (JWT) — check this

This combination lets Claude Code authenticate as a secure public client using PKCE, without a long-lived client secret sitting on your machine.

6
Restrict who's allowed to use it

Still on the Policies tab, under Plugin Policies:

Set Permitted Users to Admin approved users are pre-authorized. Under Selected Permission Set, move MCP Client User (the one you made in Phase 2) into the Selected column. Set IP Relaxation to Relax IP Restrictions. Click Save.

Why "admin approved" instead of "self-authorize" This means only users you've explicitly assigned the MCP Client User permission set to can ever authenticate through this app — not every user in the org.
7
Copy the Consumer Key

Go to the Settings tab → App Settings → Consumer Key and Secret. Verify with the code sent to your email, then copy the Consumer Key.

You won't need the Consumer Secret — with "Require secret" unchecked and PKCE required, Claude Code authenticates without one.

5
Connect Claude Code
This is where it all comes together — three commands. ~5 min
1
Add the MCP server

Open a terminal in your project folder and run:

Terminal claude mcp add --scope project --transport http \ --callback-port 8080 --client-id YOUR_CONSUMER_KEY \ salesforce https://your-instance.my.salesforce.com/platform/mcp/v1/alpha/servers/sobject-all

Swap in the Server URL from Phase 3 and the Consumer Key from Phase 4. Make sure --callback-port matches the port you set in the Callback URL.

Which --scope should I use? --scope project writes the server into .mcp.json at your project root, so it's easy to share with teammates (minus their own auth token). Use --scope user instead if you want this server available across every project on your machine, not just this folder.
2
Authenticate

Start Claude Code (claude) and run the slash command:

Inside a Claude Code session /mcp

Select salesforce from the list, press Enter, and choose Authenticate. Your browser opens to the Salesforce login screen — log in and click Allow. Back in Claude Code, the server's status flips to ✓ Connected.

Prefer doing it outside a session? This works too:

Terminal claude mcp login salesforce
3
Verify and test it

Check the connection from the shell any time:

Terminal claude mcp list

Then, inside Claude Code, just ask it something about your org:

Claude Code prompt Query the 5 most recently created Accounts in my org
✓ How to know it's working Claude should call the MCP tool and come back with real records from your org — actual Account names and dates, not a generic answer. That's the "headless" connection: no browser tab, no clicking through Setup, just natural language against live data.
★
What .mcp.json looks like when you're done

For reference, this is roughly what claude mcp add writes to .mcp.json in your project root:

.mcp.json { "mcpServers": { "salesforce": { "type": "http", "url": "https://your-instance.my.salesforce.com/platform/mcp/v1/alpha/servers/sobject-all", "oauth": { "clientId": "YOUR_CONSUMER_KEY", "callbackPort": 8080 } } } }

Your OAuth token itself is stored securely outside this file (system keychain / credentials store) — never committed to git.

6
Optional: Connect Claude (the Chat App) Instead
Prefer talking to Claude in the browser over the CLI? Same MCP server, same External Client App — just a different front door. ~5 min
Why this works so well Since Anthropic authored the original MCP specification, Claude (the chat app at claude.ai) has strong native support for the protocol — it's a solid option for quick developer testing, not just Claude Code. Everything below reuses the permission set from Phase 2 and the External Client App from Phase 4, so if you've already done those, this is a five-minute add-on.
1
Open Connectors and start a custom connector

In Claude, click Customize in the left sidebar, then click Connectors and the + button. Click Add custom connector.

Give it a name (e.g. Salesforce MCP) and an optional description.

2
Enter the server URL

Substitute the server name from Phase 3 into the format for your org type:

All production orgs https://api.salesforce.com/platform/mcp/v1/SERVER-NAME
Sandbox or scratch orgs https://api.salesforce.com/platform/mcp/v1/sandbox/SERVER-NAME

For example, to use the platform/sobject-all server in a scratch org:

Example https://api.salesforce.com/platform/mcp/v1/sandbox/platform/sobject-all
3
Add the Consumer Key and connect

Open Advanced settings and paste the Consumer Key you copied in Phase 4 into OAuth Client ID. Click Add.

Click Connect next to the connector you just created. Claude redirects to the org containing the External Client App from Phase 4 — if you're already logged in there, the user challenge is skipped and Claude gets its access token straight away.

✓ Optional: fine-tune tool permissions Once the connector authenticates, click Configure next to it to see the tools exposed by that MCP server and adjust which ones Claude is allowed to use.
4
Test it

Start a new chat and ask Claude something about your org, the same way you tested Claude Code in Phase 5 — for example, "Query the 5 most recently created Accounts in my org." A real answer with actual record names and dates means the connector is live.

Common problems
Things that catch people out the first time through this flow.
Browser opens for OAuth but the redirect fails / "connection refused"
Almost always a port mismatch. The --callback-port you passed to claude mcp add must exactly match the port in the Callback URL on your External Client App (e.g. both 8080). If they don't match, remove the server (claude mcp remove salesforce) and re-add it with the correct port — or update the Callback URL in Salesforce to match. If the browser shows an error page after you log in, copy the full URL from the address bar and paste it back into the prompt Claude Code shows — it can recover the auth code from that.
/mcp shows "Needs authentication" even after I logged in
Run /mcp again and re-select Authenticate — refresh tokens occasionally expire or get revoked (e.g. if you edited the ECA's policies afterwards). You don't need to remove and re-add the server, just re-authenticate.
Tools list is empty even though the server shows Connected
Check that the permission set (MCP Client User) is actually assigned to the user you authenticated as, and that it's listed in the ECA's Selected Permission Set. A connected-but-toolless server almost always means the authenticated user doesn't have access to that server's underlying permission set.
Claude says it can't reach the tool / times out
Double-check the Server URL from Phase 3 was copied in full and the standard server is still Activated in Setup → MCP Servers. Also confirm your org's IP restrictions on the ECA are set to Relax IP Restrictions — a strict IP range will silently block requests coming from your machine.
"Admin approved users are pre-authorized" but I still get a permission error
Go back to the permission set → Manage Assignments and confirm your user is actually in the assigned list — creating the permission set doesn't assign it to anyone automatically.

You're connected. Claude can now talk to your org.

MCP is enabled, your permission set is scoped, the External Client App is authorising real requests, and Claude Code (and/or the Claude chat app, if you did Phase 6) has a live connection to Salesforce.
Start with read-only questions, then work up to writes once you trust the flow.
